# DiPlay v0.3.17 — 车机硬件信息诊断卡片、视频参考帧抗花屏与音频延迟消除

## 更新内容

### 1. 诊断设置中新增车机硬件信息卡片与导出（Issue IKT54J）
- **车机硬件配置卡片**：在「设置 → 诊断」中新增「车机硬件信息」卡片，提供固定顺序的 `key=value` 硬件快照，方便车主拍照或对比同款车型的硬件批次：
  - 核心配置展示：SoC / CPU（架构、核心数、最高主频）、运行内存 RAM（总容量与可用余量）、存储空间、屏幕分辨率与刷新率、已挂载 USB 设备的 VID:PID 列表、系统内置 H.264 硬件解码器名称；
  - 静态性能分级评估与预设建议：以 1GB 内存、四核 996MHz 的低配车机作为中档基准标定性能等级，给出针对该硬件的最佳配置建议；
  - 隐私保护：严格杜绝采集或导出任何设备唯一标识符（不含 MAC 地址、序列号、Android ID、IMEI 或 Wi-Fi SSID）。
- **诊断报告头部摘要**：在导出的系统诊断报告头部新增一行硬件概要信息，大幅提升排查连线与卡顿问题时的分析效率。

### 2. 视频解码丢帧保持参考链与音频排队延迟消除（Issue IKT54J）
- **参考帧断裂防御与花屏消除**：
  - 当视频解码循环因性能瓶颈丢弃过期帧时，若被丢帧为后续帧的参考基准，继续送解会导致画面大面积马赛克与绿屏；
  - 现在丢帧后主动将参考帧链标记为失效，后续非 IDR 关键帧一律拒绝并立即向上游申请关键帧；
  - 在等待关键帧到达期间画面平滑停留在最后一帧完好图像，无需重构或刷新解码器，既消除了大面积马赛克，又杜绝了频繁重置解码器引发的抖动循环。
- **音频流时间排队预算与低延迟截断**：
  - 音频预解码队列此前仅依赖 192 包的硬上限且丢包策略为丢弃最新帧，在解码饥饿时导致队列长期积聚约 1.75 秒的陈旧音频；
  - 改为通过 RTP 时间戳精确度量流时间排队长度，设定 600ms 延迟预算；超过预算时严格从最老的一端剔除陈旧数据包；
  - Wi-Fi 抖动后的短时突发仍在预算内完整保留，彻底消除音画不同步与声音持续滞后。

### 3. 无线引导蓝牙慢枚举容错与适配器休眠自愈（Issue IKT54J）
- **USB 蓝牙冷启动慢枚举容错**：在无线连线引导的第 1 阶段，轮询等待蓝牙适配器出现的时间延长至最多 30 秒，彻底解决部分车机冷启动时外接 USB 蓝牙狗尚未完成枚举便过早报错并弹窗建议“改用有线连接”的误判。
- **阶段超时精准归因**：后置引导等待时间由 60 秒缩短为 30 秒，且两处超时分支明确指向实际发生超时的阶段（如 Bluetooth iAP2 超时），不再将连线停滞误报为车机热点故障。
- **蓝牙协议栈休眠唤醒重试**：当会话拆除后 USB 蓝牙协议栈被底层关闭时，引导轮询中增加了受限防抖的 `enable()` 唤醒重试，防止引导窗口降级为无作为的被动等待而导致 iPhone 无法被寻呼。

### 4. 会话阶段与倒车防挤压计时改用单调时钟（Issue #373）
- 针对部分老旧车机无硬件 RTC、冷启动时系统时间停留在 2018 年并在网络同步后发生时间数年跃变的问题，将连线阶段持续时间与倒车防挤压周期的计算全面切换至单调时钟（`SystemClock.elapsedRealtime()`）。
- 杜绝时间同步向前跳变时界面显示“已等待 278,984,999 秒”的荒谬文案，也防止时间向后校准时倒车防挤压门槛被无限锁死。
